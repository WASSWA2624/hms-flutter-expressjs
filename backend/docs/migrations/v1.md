# Database Migration and Recovery Runbook

HOSSPI database migrations are forward-only. Never edit, reorder, or delete a
migration that has been applied outside a disposable local database.

## Required change record

Every schema change must document:

- affected tables, indexes, constraints, and public API fields;
- whether existing rows require a backfill;
- expected lock duration and deployment ordering;
- pre-deployment validation and backup requirements;
- post-deployment verification;
- recovery steps and the conditions that trigger them.

Keep migration SQL deterministic. Put large or resumable data changes in a
reviewed script under `backend/scripts/` instead of one long transaction.

## Safe deployment sequence

1. Validate the schema and generate the client:

   ```sh
   npx prisma validate
   npm run prisma:generate
   ```

2. Test the migration against a production-like backup in staging.
3. Run collision, nullability, and scope checks required by the migration.
4. Take or verify a restorable database backup.
5. Deploy backward-compatible application code before destructive schema work.
6. Apply migrations:

   ```sh
   npm run prisma:migrate:deploy
   ```

7. Run the documented backfill, if any.
8. Verify row counts, constraints, indexes, public identifiers, health checks,
   and the affected API workflow.
9. Remove compatibility code only in a later deployment after verification.

## Recovery

Prefer a forward corrective migration. Name a reversing migration
`rollback_<original_change>` and test it against the same staging snapshot.

If a migration fails:

1. Stop writes to the affected workflow when continued writes could corrupt
   data.
2. Preserve logs and migration state without exposing PHI or credentials.
3. Restore from backup only when a forward correction cannot preserve valid
   data.
4. Apply the corrective migration or restore procedure.
5. Re-run backfills idempotently and verify affected public identifiers.
6. Record the incident and recovery evidence separately from application logs.

Never use `prisma migrate reset` against shared, staging, or production data.

## Friendly-ID hardening

Before adding or tightening a `human_friendly_id` constraint, run:

```sh
npm run prisma:check-hfid-collisions
```

Resolve reported collisions with an approved, backed-up procedure before
applying the constraint. Public APIs and realtime events must not fall back to
internal primary keys during migration.
